# Knowledge Garden Publisher 多博客工作区设计

## 目标

将当前只能绑定 `C:\Users\11546\Desktop\web` 的单博客应用，升级为可管理多个 Quartz 博客的桌面应用。用户可以添加本地现有博客，也可以从 GitHub 仓库下载博客；切换时保证草稿、预览、发布和 Git 状态不在不同博客之间混用。

## 范围

本次实现：

- 添加本地 Quartz 博客。
- 从 GitHub HTTPS 或 SSH 地址克隆博客。
- 持久化博客列表和上次打开的博客。
- 通过安全重载切换博客。
- 管理博客的显示名称、路径和列表成员。
- 升级时自动迁移当前默认博客。

本次不实现：

- 在应用中创建新 GitHub 仓库。
- 同时打开多个博客窗口。
- 在应用中收集或保存 GitHub Token。
- 从博客列表移除时删除本地文件或远程仓库。
- 自动把普通文件夹转换为 Quartz 博客。

## 用户体验

### 博客选择器

主界面左上角的品牌标题显示当前博客名称和下拉箭头。打开后显示：

- 已添加博客的名称、精简路径和当前标记。
- “添加本地博客”。
- “从 GitHub 下载”。
- “管理博客”。

选择其他博客时，应用先完成当前编辑器的保存，再停止预览、扫描和发布服务。目标博客通过检查后才写入“当前博客”，然后自动重启应用。如果切换失败，原博客仍然是当前博客。

### 添加本地博客

用户通过系统文件夹选择器选择目录。应用对解析后的真实路径进行检查，至少要求：

- 目录真实存在。
- 存在 `package.json`、`package-lock.json`、`quartz/bootstrap-cli.mjs` 和 `content` 目录。
- 是 Git 仓库根目录。
- 已配置可用的 `origin` 远程仓库。

如果仅缺少 `node_modules` 或依赖不匹配，应用允许添加，但在完成前明确要求使用内置 Node/npm 执行依赖安装。已添加的真实路径不重复创建记录，而是直接切换。

### 从 GitHub 下载

向导收集：

- GitHub 仓库 HTTPS 或 SSH 地址。
- 保存位置。
- 可选的显示名称，默认使用仓库名。

仅允许 `https://github.com/<owner>/<repo>[.git]` 和 `git@github.com:<owner>/<repo>[.git]` 形式。Git 作为可执行文件启动，参数以数组传入，不使用 shell 拼接。目标目录必须不存在，避免覆盖现有数据。

流程阶段为“下载中—安装依赖—检查中—完成”。Git 认证由系统 Git Credential Manager 处理，应用不获取凭据。失败时保留已生成目录以避免隐式删除，并向用户显示其确切位置；只有用户再次确认时才可处理该目录。

### 管理博客

管理窗口对每个博客提供：

- 修改应用内的显示名称。
- 打开本地文件夹。
- 切换到该博客。
- 从应用列表移除。

移除操作只更新应用配置，不删除博客目录、Git 记录或 GitHub 仓库。当前博客不能在没有另一个可用博客时被移除。

## 持久化模型

在 Electron `userData` 目录中保存一个带版本号的 JSON 文件，例如 `blogs.v1.json`。单个记录包含：

```ts
interface BlogRecord {
  readonly id: string
  readonly name: string
  readonly path: string
  readonly canonicalPath: string
  readonly createdAt: string
  readonly lastOpenedAt: string
}

interface BlogRegistryV1 {
  readonly version: 1
  readonly activeBlogId: string
  readonly blogs: readonly BlogRecord[]
}
```

`id` 使用随机 UUID，不从路径或仓库地址推导。`canonicalPath` 用于 Windows 不区分大小写的去重，不显示给用户。保存采用“写入同目录临时文件，然后原子替换”的方式。

第一次运行新版本时，如果注册表不存在，则将原有 `DEFAULT_GARDEN_PATH` 创建为第一条记录并选中。如果配置文件无法解析或校验，应用保留原文件，进入可恢复的博客选择界面，不默认清空数据。

## 进程与服务架构

工作区选择、配置文件、文件夹对话框和 Git 克隆全部位于 Electron 主进程。渲染进程只能通过经过 Zod 校验的最小 IPC 合约调用它们。

当前的发布、预览、历史、笔记和回收站服务仍然是“单工作区实例”。本次不将其改为动态多租户服务，而是在启动时从注册表取得当前路径后创建。这是选择“自动重启切换”的核心原因：每次进程生命周期仍然只拥有一个博客，避免旧的预览子进程、草稿密钥或发布任务泄漏到新工作区。

切换顺序为：

1. 渲染进程请求编辑器立即保存，并等待结果。
2. 主进程检查目标博客，不在此时改变活动记录。
3. 主进程拒绝在无法安全停止的发布任务期间切换。
4. 主进程执行现有的安全关闭流程，停止发布、扫描和预览。
5. 原子写入新的 `activeBlogId` 和 `lastOpenedAt`。
6. 调用 Electron 的重启流程。

任一前置步骤失败时都不写入新的活动博客。

## IPC 与权限边界

新增博客管理合约，包括：

- 列出已添加博客。
- 选择本地目录并检查。
- 添加或更新显示名称。
- 校验 GitHub 地址和目标路径。
- 开始、取消和订阅克隆进度。
- 切换博客并重启。
- 从列表移除非当前博客。
- 在文件管理器中打开本地路径。

所有请求继续使用已有的受信渲染进程检查。渲染进程不接收任意可执行文件、命令参数或凭据。进度事件不转发可能包含凭据的 Git 原始输出，只转发应用生成的阶段和安全错误摘要。

## 错误处理

- 注册表损坏：保留损坏文件，显示恢复界面，允许重新定位原博客。
- 博客路径失效：不启动其服务，显示“重新定位”或“从列表移除”。
- 重复路径：使用真实路径去重，直接返回现有记录。
- 依赖缺失：只允许使用经验证的内置 Node/npm 执行 `npm ci`。
- Git 认证失败：引导用户在 Windows Git Credential Manager 中登录，不索要 Token。
- 克隆失败：保留失败目录并报告路径，不自动递归删除。
- 保存失败：拒绝切换，保持当前博客和编辑内容可见。
- 服务无法停止：拒绝切换，不写入新活动记录。
- 重启失败：显示明确提示，并允许用户手动重新打开应用；下次启动使用已校验的新博客。

## 测试与验收

### 单元和集成测试

- 注册表初始化、升级迁移、原子写入、损坏配置和路径去重。
- 本地 Quartz/Git 工作区的成功、依赖缺失和结构无效分支。
- GitHub HTTPS/SSH 地址解析与非 GitHub 地址拒绝。
- 克隆目标不存在、进度转换、取消和失败保留。
- 切换时的保存失败、发布中、安全关闭失败和成功重启。
- 移除操作只改变注册表，不触碰博客目录。
- IPC Schema 对路径、名称、URL 和进度事件的边界检查。
- 博客选择器、本地添加、GitHub 向导和管理窗口的组件行为。

### 端到端测试

- 升级旧安装后自动显示现有 Knowledge Garden。
- 添加第二个临时 Quartz 博客，切换并重启后显示正确笔记。
- 使用临时本地 bare Git 仓库替代真实网络，验证 GitHub 克隆管道的参数、进度和后续检查。
- 验证移除博客后本地文件仍然存在。
- 验证切换前尚未自动保存的文章已落盘。

最终必须通过 Publisher 的完整单元测试、TypeScript 检查、Electron 构建、Playwright 端到端测试和 Windows 安装包验证。

## 成功标准

- 新用户可从本地目录或 GitHub 添加第一个博客。
- 现有用户升级后无需重新选择当前博客。
- 应用能记住上次选中的博客。
- 切换博客后，笔记列表、草稿恢复、本地预览、发布检查和历史都来自新博客。
- 失败切换不会改变当前博客。
- 任何“移除”操作都不删除用户内容。
- 应用不保存 GitHub 凭据，不通过 shell 拼接执行 Git 命令。
