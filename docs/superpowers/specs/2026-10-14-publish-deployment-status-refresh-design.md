# 发布后变化数与部署状态刷新设计

## 背景与问题

Knowledge Garden Publisher 在执行“验证并发布”后，能够成功提交并推送博客内容，但界面仍可能长期显示：

- “可发布变化：3”
- “发布成功，正在等待部署。”

实际检查表明，博客仓库已经与 `origin/main` 同步，GitHub Actions 部署也已经成功。问题来自发布器界面状态没有在推送完成后继续刷新：

1. `changeCount` 只在此前扫描变化时写入，发布完成后没有重新扫描，因此仍显示旧数量。
2. 主进程在 Git 推送完成后立即发送固定的完成消息“发布成功，正在等待部署。”，渲染进程没有继续查询 GitHub Actions 的最终结果。
3. 项目已有部署历史查询服务，可以查询当前提交对应的 GitHub Actions 运行结果，但发布流程尚未复用它。

## 目标

- Git 推送成功后立即重新扫描本地变化，使“可发布变化”显示真实值；正常情况下应归零。
- 推送成功后继续跟踪当前最新提交对应的 GitHub Actions 部署。
- 根据最终结果显示明确状态：部署成功、部署失败、部署取消，或暂时无法确认。
- 复用现有历史记录与部署查询接口，不重复实现 GitHub Actions 请求逻辑。
- 防止切换博客、关闭页面或连续发布时，旧查询结果覆盖当前界面。

## 非目标

- 不改变博客的 Git 提交、推送和分支迁移逻辑。
- 不改变 GitHub Actions 工作流或 GitHub Pages 配置。
- 不增加新的部署平台。
- 不把网络超时误判为发布失败；Git 推送成功与线上部署状态必须分开表达。

## 方案概览

采用渲染进程编排方案：保持主进程发布协议不变，把现有 `complete` 事件解释为“Git 推送已经完成”，然后由渲染进程执行两项后续工作：

1. 立即调用现有变化扫描逻辑刷新 `changeCount`。
2. 调用现有历史记录和部署查询接口，跟踪刚推送提交对应的 GitHub Actions 运行，直到得到终态或查询超时。

这样可以复用现有服务和取消机制，并把界面状态控制留在当前负责展示发布进度的组件中。

## 状态流程

发布流程按以下阶段显示：

1. 验证、提交、推送期间：继续显示主进程发送的现有进度。
2. 收到主进程 `complete` 事件：
   - 立即显示“发布成功，正在部署…”；
   - 重新扫描可发布变化；
   - 启动部署查询。
3. 查询得到终态：
   - `succeeded`：显示“发布成功，部署已完成。”；
   - `failed`：显示“发布已完成，但部署失败。”；
   - `cancelled`：显示“发布已完成，但部署已取消。”。
4. 查询超时、网络不可用、GitHub 限流或无法匹配运行记录：显示“发布成功，暂时无法确认部署状态。”。

对于无法确认的情况，发布本身仍视为成功，不显示为 Git 推送失败。若接口返回 GitHub Actions 页面地址，界面应保留可访问的检查入口。

## 部署记录匹配

渲染进程为本次跟踪生成唯一 `requestId`，然后：

1. 调用 `api.history.git({ limit: 1, requestId })` 获取本地当前最新提交。
2. 调用 `api.history.deployments(...)` 获取或等待部署记录。
3. 只接受提交 ID 与当前最新提交一致的部署结果，避免把较早一次 Actions 运行显示成当前发布结果。
4. 使用现有部署服务的轮询、终态识别、超时与可用性信息，不在 `App.tsx` 中直接请求 GitHub API。

如果当前接口一次调用已经负责轮询到终态，则渲染进程只需等待该调用返回；若返回非终态记录，则按照现有接口约定继续查询，但不得绕过服务层自行轮询 GitHub。

## 渲染进程改动

### 发布进度订阅

将 `api.publish.onProgress(setPublishProgress)` 改为包装回调：

- 普通阶段继续写入 `publishProgress`。
- 对每个发布操作只处理一次 `complete` 事件。
- 收到 `complete` 后启动变化刷新与部署跟踪。
- 本地部署跟踪消息覆盖主进程固定的“正在等待部署”文案，直到得到最终结果。

需要使用发布代次或令牌标识当前操作，避免 React Strict Mode 重复订阅、重复完成事件或异步竞态造成多次刷新。

### 变化数刷新

推送完成后调用现有 `loadChanges()`，以仓库当前状态更新 `changeCount`。刷新失败不改变“Git 推送成功”的事实，但应保留原有错误处理或给出可理解的扫描失败提示。

### 生命周期与取消

以下情况必须取消仍在进行的部署查询：

- 用户切换博客；
- 组件卸载；
- 用户开始下一次发布。

取消时调用 `api.history.cancel({ requestId })`，并递增或替换本地发布代次。异步调用返回后必须再次检查代次；过期结果不得更新当前界面。

## 错误与状态映射

| 场景 | 发布结果 | 界面阶段 | 用户文案 |
| --- | --- | --- | --- |
| Git 推送失败 | 失败 | `failed` | 保持现有发布错误信息 |
| 推送成功，部署成功 | 成功 | `complete` | 发布成功，部署已完成。 |
| 推送成功，部署失败 | 发布成功、部署失败 | `failed` | 发布已完成，但部署失败。 |
| 推送成功，部署取消 | 发布成功、部署取消 | `failed` | 发布已完成，但部署已取消。 |
| 推送成功，但查询超时或不可用 | 成功、状态未知 | `complete` | 发布成功，暂时无法确认部署状态。 |

部署失败或取消使用失败视觉状态，但文案必须明确 Git 推送已经完成，不能让用户误以为笔记没有上传。

## 测试设计

新增或调整渲染层测试，至少覆盖：

1. 收到发布 `complete` 后重新扫描变化，并把旧变化数量更新为最新结果。
2. 当前提交对应的部署成功时显示“部署已完成”。
3. 部署失败和取消时显示准确文案，并明确发布已经完成。
4. 查询超时、网络错误或服务不可用时显示“暂时无法确认”，而不是发布失败。
5. 部署返回的是其他提交时，不把它当作当前发布结果。
6. 切换博客或组件卸载时取消请求，过期结果不会更新界面。
7. 连续两次发布时，第一次的迟到结果不会覆盖第二次状态。
8. 重复 `complete` 事件或 Strict Mode 生命周期不会触发重复跟踪。

同时运行现有发布、历史记录和渲染层测试，确认主进程协议以及已有部署历史页面没有回归。

## 验收标准

- 发布并推送成功后，界面的可发布变化数量会自动刷新；无新变化时显示 0。
- 界面不再永久停留在“发布成功，正在等待部署。”。
- GitHub Actions 完成后，界面能区分成功、失败和取消。
- 无法确认线上状态时，界面不会把已经成功的 Git 推送误报为失败。
- 切换博客、离开页面或再次发布不会出现旧状态覆盖新状态。
- 自动化测试覆盖上述关键状态与竞态。
